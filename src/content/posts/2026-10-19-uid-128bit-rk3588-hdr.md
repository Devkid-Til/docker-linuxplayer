    title: "用户 ID 不再只是 32 位：内核 RFC 把 UUID / GUID 变成一等身份"
    meta: "〔10-19 02:01 北京〕· [RFC PATCH 00/41] UUID and GUID user and group ids (*_r system calls)（Jan Koester）"
    points:
      - label: 现状
        text: >-
          内核里的用户和组身份一直是 32 位数：<code>kuid_t</code>/<code>kgid_t</code>
          包着一个 <code>u32</code>，凭据、文件属主、ACL、keyring、socket 对端、
          信号发送者、procfs 与 audit 记录都以这个数字为中心。目录服务不是这样命名用户的——
          Active Directory 用 128 位 objectGUID（以及 SID），LDAP 目录常用 entryUUID。
      - label: 痛点
        text: >-
          今天所有服务这类用户的系统（winbind、sssd、nfsidmap、ksmbd 的用户态）都要把
          128 位 id 映射成 32 位：按区间、按哈希或本地数据库。映射在不同机器上不一致，
          除非处处同样配置；映射可能碰撞；写到共享存储或备份里的属主还取决于哪台机器写的。
      - label: 方案
        text: >-
          Jan Koester 的 RFC 0/41 把 <code>kuid_t</code>/<code>kgid_t</code> 换成
          tagged union（legacy 数字 / UUID / GUID），没有映射表，内核直接比较、哈希、
          存储整个 id。新增 <code>_r</code> 系统调用家族（<code>getuid_r</code>、
          <code>setresuid_r</code>、<code>setgroups_r</code>、<code>fchownat_r</code> 等），
          参数是 20 字节的 <code>__kernel_uid_r_t</code>；既有接口补上
          <code>STATX_UID_R</code>、<code>SO_PEERCRED_R</code>、
          <code>SCM_CREDENTIALS_R</code>、<code>si_uid_r</code>、
          <code>IPC_STAT_R</code>、<code>KEYCTL_CHOWN_R</code> 与 POSIX ACL xattr v3。
          文件系统必须声明 <code>SB_I_UID_R</code> 才能存这类属主：tmpfs、ramfs、devpts、
          条件性的 overlayfs，以及带只读兼容 <code>uid_r</code> 特性（256 字节 inode）的 ext4；
          NFSv4 与 ksmbd 用文本或 SID 承载。
      - label: 为什么
        text: >-
          边界划得很清楚：UUID/GUID 只存在于初始 user namespace，不进入任何
          uid_map/gid_map，在其他 namespace 里显示为 overflow id，子 namespace 的任何
          capability 都不能对它们提权；idmapped mount 原样透传。经典系统调用保持 32 位语义，
          遇到 UUID 用户返回 overflow id，跟 16 位调用处理 65535 以上的方式一致。
          20 字节结构在所有 ABI 上布局相同，因此不需要 compat 入口。
      - label: 效益
        text: >-
          目录服务给出的 id 就是磁盘上的属主，也是每个凭据里的 id，不需要映射表。
          作者给了测试：selftests 14/14，QEMU 启动测试 88/88，并在打过补丁的 libc、
          e2fsprogs、OpenSSH、rsync、ksmbd/NFS 全套上验证 UUID 用户能 ssh 登录、
          在 ext4 上拥有文件、访问 ksmbd 与 NFSv4 共享。
      - label: 下一步
        text: >-
          作者把三个问题留给评审：kuid_t 用 tagged union 是否可接受，还是把 128 位 id
          放在 u32 kuid_t 旁边；20 个 <code>_r</code> 调用是否该合并成一个
          <code>setid_r(which, ...)</code>；以及是否按子系统拆成 core/fs/net/ext4/nfsd
          几批。系列基于 v7.3-rc7，系统调用号 473–492 只是占位。
    verdict: "这不是加一个特性，而是拆掉「uid 是 32 位」这个贯穿几十年的假设。能否合入取决于维护者对 kuid_t 布局与 ABI 扩张的容忍度，但它已经把「目录身份直接落到磁盘」这条路径完整走通了。"
    link: "https://lore.kernel.org/netdev/<cover.1792346472.git.jan.koester@gmx.net>/"

    title: "RK3588 的 HDR 缺口：HDMI 连接器终于能声明 BT.2020"
    meta: "〔10-18 22:32 北京〕· [PATCH v4 0/7] drm: Add colorspace property support to the HDMI helpers（Jan Claußen）"
    points:
      - label: 现状
        text: >-
          DRM 的 HDMI 连接器通过 <code>drmm_connector_hdmi_init()</code> 初始化，
          负责向用户态暴露色彩空间与 HDR 相关属性。问题是这条 helper 路径一直没有创建
          <code>colorspace</code> property。
      - label: 痛点
        text: >-
          用户态合成器需要这个 property 来声明 BT.2020。没有它，KWin 这类合成器
          不会提供 HDR 选项——即使底层 HDMI 控制器和屏幕都支持。
      - label: 方案
        text: >-
          v4 七补丁让驱动声明自己支持哪些色彩空间，由 HDMI helper 统一创建 property，
          并在值变化时强制一次 modeset；bridge connector 把支持列表传给 HDMI helper；
          rockchip 的 dw_hdmi_qp 转发平台数据里的支持列表，并从连接器的色彩空间设置
          VOP2 的 color space，最后声明 BT.709 与 BT.2020。
      - label: 为什么
        text: >-
          v3 按 Maxime 的意见把处理搬进 HDMI helper，并改成「驱动声明」而不是
          「向用户态暴露全部」；v4 按 Sashiko 的评审补上 VOP2 色彩空间，
          让 YCbCr 输出使用匹配的转换矩阵。改动总量不大（8 个文件、+58/−5），
          因为这层抽象本来就在。
      - label: 效益
        text: >-
          作者在 Radxa Rock 5B（RK3588）+ LG OLED55B87LC 上、KDE Plasma 6.7.5 里
          验证 BT.2020 RGB 可用；dw-hdmi-qp 是第一个用户。
      - label: 下一步
        text: >-
          目前只测了 BT.2020 RGB。更多色彩空间需要各驱动声明并补测试；对 RK3588
          的 HDR 支持来说，这是上游第一次有完整路径。
    verdict: "这是 helper 建 property、bridge 传能力、VOP2 设矩阵的三层配合。单独看每一层都很小，合起来才是 HDR 从驱动到合成器的一条通路。"
    link: "https://lore.kernel.org/dri-devel/<20261018143135.5745-1-jan.claussen10@web.de>/"

    title: "「同一用户」的检查收进一个文件：12 处 uid_eq 不再各写各的"
    meta: "〔10-19 01:31〕· [PATCH 00/13] cred: gather the same uid checks between tasks in one place（Josef Bacik）"
    points:
      - label: 定位
        text: >-
          内核里有十几处允许一个任务操作另一个任务的检查：<code>kill()</code>、SIGIO、
          sched 系统调用、<code>setpriority()</code>、<code>ioprio_set()</code>、
          <code>prlimit()</code>、ptrace、cgroup v1 迁移、resctrl、
          <code>KEYCTL_SESSION_TO_PARENT</code>。每一处都手写几个 <code>uid_eq()</code>，
          而且分六种口味：看 real/effective/saved 的哪些、euid 0 是否放行。
      - label: 做法
        text: >-
          Josef Bacik 的 13 补丁把它们收进 <code>kernel/cred.c</code>，提供
          <code>cred_ids_allow_signal</code>、<code>_sigio</code>、<code>_sched</code>、
          <code>_control</code>、<code>_move</code>、<code>_ioprio</code> 等 helper，
          并附一张「哪条规则看哪些 id」的表；逐个转换调用点。唯一不是纯替换的是
          fcntl <code>F_SETOWN</code>：它改为持有 cred 引用，而不是复制 uid/euid。
      - label: 效益
        text: >-
          行为按设计完全不变（这些语义已经是 ABI），附 KUnit 测试逐项对照原表达式；
          作者还在 KASAN + lockdep 下跑了 64 种 real/effective/saved 组合、共 576 个结果，
          前后一致。意义在于：当「同一用户」的定义要改时，只有一处需要改。

          分配 per-request bounce buffer。前半段还有一批压缩后端的内存与错误路径修复。

        text: >-
          独占 zstd 的后台读：IOPS 391k→1064k（2.7x），平均延迟 49.07→9.68 µs，
          最大延迟 3.21 s→5.88 ms；共享 lz4：972k→1466k（+50.9%），最大延迟
          2.20 s→6.44 ms。

  - type: divider
    label: "📖 本期概念速查"
    kind: primary
  - type: toc
    items:
      - label: kuid_t / kgid_t
        text: 内核里的用户/组 id 类型，当前是包着 u32 的结构；本 RFC 想把它变成 legacy/UUID/GUID 的 tagged union。
      - label: UUID / GUID
        text: 128 位标识符。UUID 按 RFC 9562；GUID 是微软的字节序变体，常出现在 Active Directory 的 objectGUID 中。
      - label: _r 系统调用
        text: 与经典 getuid/setuid/chown 等并列的新家族，用 20 字节结构承载 128 位 id，所有 ABI 布局一致。
      - label: SB_I_UID_R
        text: 文件系统级标志，表示该文件系统能存 UUID/GUID 属主；没有它的文件系统在 chown 与创建文件时返回 EOVERFLOW。
      - label: colorspace property
        text: DRM 连接器的属性，用户态用它声明 BT.709/BT.2020 等色彩空间；HDMI helper 统一创建。
      - label: VOP2
        text: Rockchip 的显示控制器；从连接器取色彩空间后，YCbCr 输出会使用匹配的转换矩阵。
      - label: dma-buf
        text: 跨设备共享缓冲区的内核对象，常用于 camera→ISP→GPU 的零拷贝链路。
      - label: XDP multi-buff
        text: 让 XDP 程序在由多个描述符组成的一帧上运行，而不是只看第一个缓冲。
      - label: AF_XDP zero-copy
        text: 把网卡收到的帧直接送进用户态 socket 内存区域；当前 stmmac 对 multi-buff 帧仍直接丢弃。
      - label: zcomp
        text: zram 的压缩后端抽象，管理压缩/解压上下文与 per-CPU stream。
