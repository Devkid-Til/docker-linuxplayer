虚拟机里的摄像头，终于要成标准设备了

〔08-06 01:33 北京〕· virtio-media 驱动 v6

  • • 现状：虚拟机的网卡、磁盘、显卡各有标准 virtio 设备（virtio-net/blk/gpu），但相机、采集卡这类媒体设备没有标准类型，V4L2 里也没有接入 virtio 的路径。
  • • 痛点：云厂商想给云主机提供摄像头/采集能力，只能靠私有方案或设备模拟，复用不了 virtio 成熟的队列 + 共享内存机制，用户态也接不进标准 V4L2 接口。
  • • 方案：新增 virtio-media 驱动（Google 主导）：新 virtio 设备类型 + V4L2 驱动骨架，含 session 管理、scatterlist 构建、ioctl 逻辑与 USERPTR 内存支持。
  • • 为什么：与其每个云厂商自造轮子，不如把媒体设备定义成标准 virtio 设备，统一走 virtqueue + dma-buf 共享内存。
  • • 效益：VM 里能用标准 V4L2 接口访问虚拟摄像头/采集设备——云游戏、远程桌面、云端 AI 摄像头都有了基础设施。
  • • 下一步：v6 迭代中，设备类型还要在 virtio spec 里定稿。新框架，正缺参与者。

一句话点评：云上音视频是明牌，virtio-media 就是在铺这条路。做视频方向的值得盯。

Rust 正在让 GPU 同步「不可能出错」

〔08-05 23:01 北京〕· rust / dma_buf: dma_fence 抽象 v9

  • • 现状：dma_fence 是内核里表示「一次 DMA 完成/失败」的同步原语，GPU/显示/相机驱动靠它协调共享内存的读写进度；Rust 内核正在把子系统接口封装成安全抽象。
  • • 痛点：Rust 驱动要和 C 侧 dma_fence 交互却无安全抽象——生命周期靠手动管理，引用计数一错就是 UAF/泄漏；RCU 等待也缺 Rust 封装。
  • • 方案：新增 Rust dma_fence 抽象（含 ARef<T> 的 ForeignOwnable、rcu_barrier 抽象、补全错误码），并新增 MAINTAINERS 条目。
  • • 为什么：把 dma_fence 封装成类型安全的引用计数对象，让编译器管生命周期而不是靠人肉；RCU 等待一并安全化。
  • • 效益：用 Rust 写 GPU/显示/媒体驱动时能安全使用同步原语，dma-buf 这条 mm ↔ 驱动大动脉先打通。
  • • 下一步：v9 接近合并窗口。想入坑 Rust 内核，这是入口级补丁集。

一句话点评：Rust 化不是炫技——GPU 是最容易出 UAF 的地方，交给编译器兜底。

📖 本期速查：9 个词看懂今天

  • • virtio：虚拟化里收发数据的标准机制（virtqueue + 共享内存），virtio-media 是其媒体设备扩展
  • • dma_fence：表示一次 DMA 完成/失败的同步原语，共享内存设备的读写进度靠它协调
  • • migrate_device：设备私有页（如 GPU 显存）迁回系统内存的机制，mm 与设备驱动的跨域通道
  • • THP 拆分：透明大页在迁移/分裂时拆成普通小页
  • • dma-buf：跨设备共享内存的抽象，mm 与驱动的桥
  • • v4l2_subdev：V4L2 里代表单个设备节点（sensor/加解串器/ISP 各一个）的抽象
  • • Starvis 2：Sony 汽车/监控级 CMOS 传感器系列（IMX6xx）
  • • nouveau / nova：NVIDIA 的开源驱动（nouveau 老牌 C 驱动；nova 新一代，内核部分用 Rust）
